A few minutes to your first run

Start local. Break it on purpose.

Requires Docker Compose and k6 ↗

Boot the demo shop

docker compose up -d --build
curl localhost:8000/health

The app starts on port 8000 with atomic purchasing enabled.

Run both checks

k6 run scenarios/load/products.js
k6 run scenarios/concurrency/oversell.js

Both scenarios should pass with the default configuration.

Turn on the race

docker compose down -v
BUY_MODE=naive docker compose up -d --build
k6 run scenarios/concurrency/oversell.js

The concurrency threshold now catches the intentionally unsafe path.

Good to know

Questions before the first run.

Does this run tests against my production app?

No. The included workflow builds a demo app in CI. For your project, replace its startup step and choose the target environment carefully. The load scenario can also target a URL using TARGET_URL.

What does the concurrency test actually prove?

It counts successful purchases during a 100-user rush and enforces exactly 10 successes for 10 available items. The check is about a business invariant, not just whether the endpoint returns a response.

Why does the naive example fail?

It reads stock and writes the decremented value separately. Concurrent requests can all read the same stock before any update lands. The atomic path uses a conditional database update instead.

Is there a hosted dashboard or baseline comparison?

Not in this v1. It is a small open-source CI starter: load test, concurrency test, demo app, and a pull request workflow.
